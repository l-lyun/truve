# Outbox 폴링·확장 실험 — 부분 완료 및 성능 수치 채택 보류

2026-09-08, 로컬 MySQL·Kafka·JVM. 이 보고서는 의도적으로 성능 개선율을 제시하지 않는다.

## 완료된 실제 측정값

각 행은 1,000건. 모든 완료 행에서 실제 Kafka 누락·중복 0, Outbox failed/stale/recovered 카운터 증가 0, DB retry_count 0을 확인했다.

| 폴링 / Relay | 반복 | 관측 소진 시간 | 발행 기록 지연 p99 |
|---|---:|---:|---:|
| 3초 / 1개 | 1 | 31.265초 | 30.980초 |
| 3초 / 1개 | 2 | 30.263초 | 30.096초 |
| 3초 / 1개 | 3 | 30.679초 | 30.401초 |
| 1초 / 1개 | 1 | 68.037초 | 47.874초 |
| 1초 / 1개 | 2 | 12.934초 | 12.313초 |

1초의 빠른 한 회만 골라 3초 기준선과 비교하면 선택 편향이다. 따라서 “약 58% 단축”, “2배 이상 향상” 같은 개선 문구를 쓰지 않는다. 1초의 세 번째 반복은 중단되어 이 표와 5,000건 검증 수치에서 제외했다.

3초 조건의 30.209초 유휴 관찰에서는 실제 선점 SELECT 20회, **0.6621회/초**였다. 1초 조건의 유휴 관찰은 의도한 30초가 호스트 지연으로 43.264초까지 늘어났고 48회, 1.1095회/초로 관찰됐다. 이를 정상 조건의 비용 비교로 해석하지 않는다. MySQL cgroup CPU와 JVM 누적 CPU 원시값도 저장했지만 비용 절감율이나 금액으로 환산하지 않는다.

## 왜 중단했는가

- 1초 조건 워밍업의 300건 처리에 72.087초가 걸렸다. 해당 로그에는 Kafka `NOT_LEADER_OR_FOLLOWER` 및 producer 내부 재시도 경고가 있다.
- 09:07 호스트 load averages가 267.90 / 187.26 / 156.33이었다. 동시에 시스템 검사·디스크 이미지·가상화·시뮬레이터 등 다른 작업의 CPU 사용을 관찰했다. 특정 프로세스 하나를 원인으로 단정하지는 않는다.
- 이후 본측정도 68.037초와 12.934초로 크게 달랐다. 첫 반복은 관측 소진 시간과 마지막 발행 기록 시각 사이에도 약 20초의 차이가 있어 관찰 과정까지 지연됐음을 보여준다.
- 자원 추가·다른 앱 종료로 환경을 바꾸지 않고 실험 프로세스만 중단했다. 이 상태에서 반복 수만 늘리는 것은 포트폴리오용 개선 수치의 근거가 되지 않는다.

애플리케이션 ERROR 로그 0 또는 Outbox retry_count 0을 **Kafka 오류·내부 재시도 0**이라고 표현해서는 안 된다.

## 독립 검산

`verify_matrix.py`로 완료한 5개 run의 원본 DB TSV와 Kafka TSV를 다시 대조했다. DB 상태·claim 해제·retry·payload·연속 offset·키 집합·건수·p99·관찰 타임라인이 일치했다. 별도 읽기 전용 리뷰에서도 원본 before/after Prometheus 5쌍을 재계산해 published 각 1,000건 및 failed/stale/recovered 증가 0을 확인했다.

```json
{
  "raw_data_verification": "PASS",
  "completed_blocks": 1,
  "completed_runs": 5,
  "measured_events": 5000,
  "application_error_log_count": 0
}
```

`summary.json`은 완료된 설정 블록만 포함하므로 3초 블록 하나다. 1초의 완료 두 회는 `c2-1000ms-1relay-r1-summary.json`, `c2-1000ms-1relay-r2-summary.json`과 대응 원본 파일에 있다. `failure.json`의 KeyboardInterrupt는 오류를 숨긴 것이 아니라 호스트 상태를 보고 명시적으로 중단한 기록이다.

## 포트폴리오에 지금 쓸 수 있는 범위

> 로컬 실환경에서 Outbox 이벤트 1,000건씩 5회 전달을 검증해, 입력 5,000건과 Kafka 수신 결과의 일치 및 누락·중복 0건을 확인했다.

이 문장은 이번 완료 표본의 전달 검증일 뿐, 운영 무유실 보장이나 exactly-once, 예약·결제 업무 멱등성 검증은 아니다. 기존 선점 직후 Relay 강제 종료 20건 복구 실험은 별도 장애 내성 근거로 함께 제시할 수 있다. 이번에는 성능 개선·확장성 문구를 아직 추가하면 안 된다.

## 남은 일과 재실행 보호 장치

1. 무거운 병행 작업이 끝난 안정된 호스트에서 전체 비교를 다시 실행한다. 유료 인프라가 필요하다는 결론은 아니다.
2. 3초/1초/0.3초 단일 Relay를 동일 조건으로 각각 3회 측정하고 유휴 선점 SELECT/s와 비교한다.
3. 동일 폴링에서 Relay 1개/2개를 비교하고 양쪽 개별 발행 기여 및 실제 Kafka 누락·중복을 확인한다.
4. 마지막 기준선 재확인까지 완료한 후 중앙값과 범위를 기준으로 개선 수치 채택 여부를 결정한다.

후속 스크립트에는 시작·매 회차 전 `1분 load > 논리 CPU 수 × 2`이면 중단하는 보수적 가드를 추가했다. 조건 통과가 환경 격리를 보장하지는 않는다. 회차별 호스트 스냅샷과 topic context도 남기도록 보완했다. 이 보호 장치는 이번 실행 후 추가했으며, 당시 실행 코드는 `harness.py.txt`에 그대로 보존했다. 측정 보조 함수 테스트 8개를 실행했고, 애플리케이션 소스는 이번 턴에서 변경하지 않았다. 전체 Java 테스트는 이번 턴에 재실행하지 않았다.

## 종료 후 복원 확인

기본 프로필과 3초 폴링으로 서버를 재시작했고 `/actuator/health/readiness`에서 `UP`을 확인했다. 남아 있던 600건도 처리되어 DB의 MATRIX 행은 6,600건 모두 PUBLISHED, 전체 미처리 이벤트는 0건이다. 이 6,600건은 워밍업 600건과 본측정용 6,000건을 포함한다. 중단된 세 번째 1초 반복은 재시작을 거쳤고 완결된 Kafka 원본 검산 세트가 없으므로, 성능 표와 엄격히 검산한 5,000건에 추가하지 않았다.
