## 해석

Relay 1개가 최대 100건을 처리한 뒤 3초를 기다리는 기본 설정이다.
처리 자체에 시간이 전혀 들지 않더라도 지속 backlog 처리량의 근사 상한은 100/3 = 33.3건/초다.
이번 약 30건/초는 이 설정과 일관된다. JVM·MySQL·Kafka의 최대 성능 측정은 아니다.

1,000건을 한꺼번에 넣었으므로 뒤쪽 이벤트에는 여러 배치의 대기가 누적된다.
p99 약 32초를 HTTP API 응답시간으로 표현하면 안 된다.
다음 성능 비교에서는 batch 또는 polling 간격 하나만 바꾸고 DB 부하와 함께 측정하는 것이 자연스럽다.

## 측정 정의와 범위

- 소진 시간: seed 직전부터 전체 PUBLISHED 관측까지. 1초 polling과 명령 실행 오차 포함.
- 처리량: 1,000 / 소진 시간. Kafka 브로커 최대 throughput이 아니다.
- 지연: `published_at - created_at`. published_at은 Kafka 응답 확인 뒤 조건부 UPDATE 직전의 애플리케이션 시각.
  정확한 DB 커밋 시각이나 Consumer 업무 완료 시각은 아니다.
- 실제 Relay와 실제 Kafka를 사용했지만, 입력은 독립 key의 `{}` payload를 전용 DB에 직접 적재했다.
- 같은 예약의 순서, 중복 비즈니스 변경, Kafka 장애, Backoff/Jitter 효과는 이번 측정에서 검증하지 않았다.
- 단일 로컬 JVM과 공유 Docker 환경이며 CPU/메모리 제한은 고정하지 않았다.
- 미커밋 계측 변경을 포함하며 기준 HEAD, 소스 차이, 이미지 식별자는 metadata.json 및 source.diff에 기록했다.

원본: summary.json, 이벤트별 CSV, 상태 polling JSON, 실행 전후 Prometheus snapshot.
